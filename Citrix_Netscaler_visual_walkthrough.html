01 / Remote access

Your work computer can be somewhere else.

Imagine opening your usual work desktop from a laptop at home. The applications run on a central computer in a data centre or cloud service. Your laptop shows the screen and sends back your typing and mouse clicks.

This is virtual desktop infrastructure, or VDI. NetScaler Gateway sits on the route between you and that desktop, helping check who you are and which resources you may use.

NetScaler is also used to deliver other applications and distribute traffic across servers. VDI is one example, not a requirement for this vulnerability.

02 / Remote access

People outside the office need a way to connect.

The organisation gives its gateway a public address and allows web traffic to reach it through a firewall. Remote staff connect using HTTPS, which encrypts the connection.

The gateway must receive some information before it can check a person’s identity. An unknown sender can therefore reach the login service too, even without a working account.

This attack did not need a successful login. A password or a second login factor cannot by itself fix a flaw that can be reached before authentication.

03 / Remote access

A web request comes with a browser label.

When a browser contacts a website, it sends a small amount of descriptive text called a User-Agent. This often identifies the browser and gives clues about the device or operating system.

The label changes between browsers and devices. It is not a passport: software sending a request can choose what this text says. The gateway may record that text in its activity logs.

Modern browsers may deliberately reduce the detail in this label. That does not change the important point: it is text supplied by the sender.

04 / Remote access

How does “hello” become “aGVsbG8=”?

Base64 is a way of writing the same information using an alphabet of 64 characters. It uses uppercase and lowercase letters, the digits 0 to 9, and the symbols + and /.

The computer takes the message’s underlying bits and groups them differently. Each group becomes a character in that alphabet. Nothing is made secret, and anyone can reverse the process.

In this attack, Base64 carried commands as text in the User-Agent. This can help preserve spaces, quotes and punctuation while the message passes through software and logs. The commands still needed to be decoded and executed.

The example uses lowercase hello, without a space or a line break. Base64 works on the whole sequence of bytes, not by replacing each letter with one other letter.

Why is there an equals sign?

The final two letters, lo, contain 16 bits. Adding two zero bits completes three groups of six: 011011, 000110, 111100. These give bG8. One = fills the remaining position in the four-character block. It is padding, not part of the message.

Encoding is not encryption. No secret key is needed.

Encoding makes a command less readable at a glance. It does not make it run or guarantee that security tools will miss it. The packaging benefit is an explanation of the technique, not a stated attacker motive.

05 / The break-in

The attackers left instructions in two sets of logs.

CERT-EU found repeated requests carrying encoded commands in the User-Agent. These became entries in the web request log.

In parallel, crafted login input produced a different log entry that looked like a system failure. This was the trigger: it referred back to the stored commands.

The attackers kept submitting it because the diagnostic program used the last matching failure record when it eventually ran.

watchTowr observed that the diagnostic program could take up to 24 hours to run. This is not a guaranteed waiting period on every device.

06 / The break-in

A diagnostic program mistook text for instructions.

The program ns_monuploadd_err.pl searched the logs for a crash-file name. The vulnerable version inserted text taken from a log into a system command without safely separating the two.

That let the attacker’s added text become a command. watchTowr found that it ran with root privileges, meaning very broad administrator-level authority on the appliance.

In the observed chain, the trigger then retrieved the stored web-log payload, decoded it and ran it. The original web request did not execute the commands on arrival.

07 / After the break-in

Shell access means being able to tell the device what to do.

A NetScaler is a specialised computer, with an operating system, files and programs. A shell is a program that accepts written instructions and asks the operating system to carry them out.

With the root-level command execution demonstrated here, an attacker is no longer limited to the public login page. They can act on the appliance itself. They do not need to open a normal remote-desktop window to do that.

“Root on this appliance” does not mean “administrator of every computer in the organisation”. Other systems still have their own access controls.

08 / After the break-in

PHP can run website code. Here, it ran the attacker’s code.

PHP is a programming language used to make websites do things on the server. For example, PHP code can process a form or build a page from stored information. The browser receives the result; the PHP code runs on the server, not on the visitor’s laptop.

The NetScaler also has a web server. After gaining control, the attackers changed its configuration to enable php_engine, then placed a malicious PHP script where it could receive requests from the internet.

That script was a web shell: a way to send more instructions to the appliance through web requests, without necessarily repeating the original exploit.

Enabling PHP was not the original vulnerability. The danger was letting the server execute code that the attacker had supplied. A script’s powers depend on the account and permissions it runs with.

09 / After the break-in

Now step back and look at the rest of the network.

A DMZ, or demilitarised zone, is a separate network area for services that must be reachable from outside. It acts as a buffer between the public internet and internal systems.

The gateway needs selected connections into the organisation to do its job. A compromise puts the attacker on a machine that already has that network position. This is the beginning of a foothold, not proof that every system is compromised.

The useful question is: “From this particular appliance, which other services could an attacker actually reach?”

10 / After the break-in

Reaching another system is not the same as controlling it.

From the gateway, an attacker can try to contact systems that are reachable from its network location. Moving onward into other computers is often called lateral movement.

For example, using a remote login service normally requires both a permitted network route and an account that the other system accepts. Stolen credentials, excessive trust or another vulnerability can change what is possible.

Good separation still helps after one device has been compromised. It limits which systems an attacker can contact and makes further access harder.

11 / After the break-in

The consequences can extend beyond a broken login page.

Control of the gateway may let an attacker interfere with the services it runs, examine information available to it, or alter its files and settings.

These are possible consequences to investigate. Their extent depends on the deployment, the attacker’s permissions and what actually happened. A suspicious request alone does not prove successful execution.

Network-wide compromise is a conclusion supported by evidence, not an automatic consequence of shell access to one appliance.
Sources: 16, 12, 11
Three questions for an incident team

Could work be interrupted?

Changes to services or configuration could disrupt remote access and applications.

What information was available?

Check accessible configuration, secrets, keys and session information. Do not assume the gateway can see every document or decrypt every connection.

Could the attacker conceal activity?

Files and local records might be changed. Logs kept independently of the appliance can help investigators check what occurred.

An attacker-controlled gateway is serious. The investigation still needs to establish the actual scope.
12 / Understanding the response

It was a zero-day before the fix was available.

A zero-day attack exploits a vulnerability before a fix is available. These reports describe exploitation during that period. Installing a later patch does not tell us whether someone had already entered.

Citrix published its bulletin on 27 September 2026. CERT-EU and watchTowr published the detailed reports on 28 September. This briefing reflects the information checked on 29 September 2026.

DTLS is a protocol for protecting certain network traffic. It is relevant to the second vulnerability, not a required step in the log-injection chain.

13 / Understanding the response

Updating the software and checking for intruders are different jobs.

CERT-EU recommends updating affected appliances and assessing internet-exposed devices for compromise. Both matter: an update closes a vulnerability, but an attacker may already have changed the system.

The response needs a clear owner, a plan for keeping essential services available, and evidence that the affected environment is trustworthy again.

Do not treat “the patch is installed” as a complete incident-closure statement.
Sources: 4, 3, 1, 12
Work that needs to happen together
01

Find and contain exposure

Identify affected gateways and public services. Agree how to reduce exposure without losing essential access.

02

Preserve and investigate

Secure useful evidence. Look for suspicious logs, changed configuration, unexpected scripts and signs of further access.

03

Update and restore trust

Apply the vendor’s fixes. Remove persistence and address affected secrets where necessary; recovery may require rebuilding.

A useful question for the next briefing

“Which systems were exposed, what evidence have we checked, and what supports our conclusion that access has been removed?”
